# 段落重写：避免“看似长篇，实际只是代码说明”

以下是**虚构教学片段**，仅展示写作方法，不代表真实的 Codex 接口或运行记录。

## 例 1：从口号变成设计推导

**薄弱版：**

> 我们现在引入 Bridge。Bridge 可以处理事件，提高性能。创建 bridge.py，然后运行即可。

**改写版：**

> 想象 Agent 在五秒内连续修改四个文件。如果每触发一次 Hook 就从头扫描整个仓库，扫描工作会和 Agent 的工具执行相互竞争资源。我们需要把“收到事件”和“做昂贵检查”拆开：Hook 只写一行结构化日志并立即返回，Bridge 则在短暂的事件间隔后批量扫描。这里选择的不是“速度更快的检测算法”，而是一种异步解耦。实验时连续写入多条模拟事件，记录 Bridge 实际扫描次数：如果每条事件都导致全盘扫描，这个设计目标就没有实现。

差别：真实痛点、成本机制、设计取舍、可检验目标。

## 例 2：从“测试过了”变成证据规则

**薄弱版：**

> Watchdog 判断测试是否通过，很智能，可以知道任务完成。

**改写版：**

> `pytest` 返回 0，只能说明它在当时的环境里完成了所执行的断言。我们保存测试开始和结束时的工作区指纹，并在后续检查时与当前指纹比较。如果代码变了，就把旧结果标记为 `STALE`。你可以先运行一次成功测试，之后手工追加一行注释，再查询状态。注意 `STALE` 并不意味着代码有错，它表示旧测试不再直接证明当前快照满足同样的检查要求。

差别：具体字段、观察实验、精确边界。

## 例 3：从泛泛排错变成决策树

**薄弱版：**

> 如果没看到结果，重新安装 Python 或重启电脑。

**改写版：**

> 首先只测试 Logger：用管道送入一条固定 JSON，检查 `events.jsonl` 是否新增。若没有，重点检查启动脚本里的解释器绝对路径与文件写入权限。若 Logger 正常，再启动 Bridge，观察它是否过滤了不属于目标仓库的 `cwd`。如果模拟事件能触发扫描而真实 Codex 没有，最后才去核对 Hook 配置、信任状态和触发路径。按这个顺序排错，能把问题限定在最小模块里。

差别：按依赖链定位，不从重装开始。
