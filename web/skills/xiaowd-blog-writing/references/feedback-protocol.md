# 从“这篇质量不高”到可复用写作规则

## 维护目的

Skill 是版本化知识包，不是自动记住任何反馈的魔法开关。用户的新反馈只有在被明确写入相关 `references/`、测试用例或模板，并在下一轮写作中实际应用，才算真正沉淀。

## 每次反馈的转化步骤

1. **引用原反馈**：例如“文章都是空话，没有说明 Bridge 为什么需要 debounce”。不猜测隐藏动机。
2. **定位可观察失败**：本段没有失败场景/设计取舍；或者正文示例 `bridge.py` 与仓库接口冲突。
3. **抽象成跨主题规则**：引入新设计必须提供“失败场景→原理→替代方案→测试”，而不是把“Bridge”硬写进所有未来博客。
4. **制作反例与正例**：放入 `references/rewrite-examples.md` 或评估案例。
5. **自动化可检测的部分**：通过 `scripts/lint_blog.py` 增加静态检查，但不要把语义质量冒充静态工具能检验的内容。
6. **更新版本并回归测试**：更新 CHANGELOG，在不同话题上验证不会触发过度/误伤。

## Feedback Log 模板

```markdown
### 反馈日期 / 关联文章
- 原始反馈：
- 具体失败行为：
- 新增规范：
- 对应修复示例：
- 自动或人工检查：
- 是否已复验：
```

## 防止 Skill 失控

- 不因单一一次主观评价强制所有文章长达数万字。
- 不自动上传/推送用户 Skill 修改；需得到相应授权。
- 没有充分来源时，把新规则写成建议或可选模式，不冒充用户长期稳定偏好。
- 避免把私密的个人材料、源代码或账号数据写入可公开分发的 Skill 包。
