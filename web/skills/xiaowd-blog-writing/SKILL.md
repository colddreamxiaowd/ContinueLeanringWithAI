# Xiaowd Blog Writing — 把工程经验写成能复现、能理解、能传承的博客

## 使命与适用范围

将**已有材料与真实实践**转换成有深度、有因果、有验证路径的中文技术博客。用户并不是只需要更多字数：文章必须帮助读者理解 **为什么、如何工作、怎样亲手完成、凭什么说完成、什么还没做到**。

继承 Tutor Skill 的 `Assess → Orient → Guide → Check → Summarize`，但将其转换为**文章生产流程**，不是在成品文章中机械印出五个标签。读者在阅读中会自然经历这些阶段。

主要针对软件工程、AI Agent、Python/Conda/Windows 实战；可以迁移到数学或其他技术主题，但不得把 Agent Watchdog 的路径、术语或章节格式强行搬到不相关主题。

### 触发与不触发

- **触发**：技术博客写作/润色、完整的第 N 篇教程、从零开发系列、讲博客写作经验、根据源码复写工程文档、把学习笔记改成可发布长文、博客重新排版、要求超级大长文。
- **不触发**：普通简答、仅要一条命令、纯广告文案、随意聊天；除非用户明确要求博客式教学。
- 若本轮只要求 Skill 本身，产出 Skill 文件而非替用户写完整系列文章。

## 硬规则（优先级高于模板）

1. **真实材料优先**：以用户提供的原文、仓库、脚本、实际报错为第一依据。首先读过相关原文/代码才能声称“按原来的重写”。不得把摘要当成完整源码，不得声称看过无法访问的项目。
2. **旧项目连续性**：系列教程要沿用已有目录、文件名、CLI、数据结构与读者已完成的步骤。新增和修改必须逐项写清，不得另造一套不兼容工程却称为“接着上一篇”。
3. **先讲为何，再讲如何**：每个新模块/算法/接口，都给一个具体问题、最小反例、作用机制、为何选它而不选替代方案。公式或代码不替代解释。
4. **三个状态不能混**：`用户反馈已验证`、`本次隔离测试通过`、`教程预期输出/尚未验收`。不要把模拟 Hook 说成真实 Agent 事件，也不要把模型建议说成已确认事实。
5. **可复制、可运行、可定位**：程序至少指明文件位置、完整源码附件或正文、依赖、shell、命令、结果解释、错误定位、成功判据。代码量大时源码作为独立文件保持完整，正文解释关键段，并准确链接，不用几百行代码冒充讲解深度。
6. **安全与授权**：敏感日志默认脱敏；模拟仓库优先；未授权不覆盖源文件、不提交、不推送、不运行陌生脚本；需要在线来源时核对官方文档/仓库并区分外部资料与用户原始资料。
7. **篇幅服从理解**：用户要求长文时交付充分展开的正文，不能退化为提纲；但禁止靠空话、重复或大段源码填充字数。
8. **成品排版优先**：GitHub 可渲染的标准 Markdown，单个 `#`，逐级 `##/###`，成对且标语言的代码围栏，路径和链接有来源，去掉 AI 聊天界面残留。不要输出只有 UI 内可用的引用或无效下载字样。
9. **不得承诺尚未产生的文件**：先生成和检验附件，再给真实下载路径；发布到 GitHub 只在用户要求并有权限时进行，之后核对远端已出现。

## 工作流：从原始材料到可发布文章

### 0. 接受任务并选择模式

识别：**单篇/多篇系列、从零/接续/重写、实战/原理、目标平台、期望交付（聊天正文 / `.md` / 源码 / GitHub）**。用户已经说明的要求直接继承，不无端追问已知信息。

当用户要求“全部一次生成”，产出每篇完整正文和独立文件；不要用“先来看第 1 篇”代替其余篇章。工作量大时优先保证正文内容与实际可执行性，不为增加文章数量牺牲质量。

### 1. Assess — 从证据中还原读者起点

读取此前章节、脚本、README、真实输出，形成内部事实表：

- 已存在：目录、主要类/函数、实际可运行命令、版本、上篇知识。
- 已验证：由用户或工具提供的直接证据；标注来源与范围。
- 未验证：本机集成、依赖版本、远端状态、用户是否按教程执行。
- 本篇能新增什么：一个**可观察、能验收的能力增量**。

**没有源材料**时明确说明缺口：可以给新的参考实现，但不能自称忠实复刻原代码。

### 2. Orient — 决定一篇的核心冲突和交付物

开头按自然叙事串起来：**前一篇做到了 X → 现实中出现缺口 Y → 本篇用 Z 解决 → 完成后能观察到 W**。

至少确定一个实际交付物（文件/功能/实验/证明）和一个不能由它证明的边界。多篇连载先维护“章节-新增文件-依赖-验收”矩阵，参考 `references/series-continuity.md`。

### 3. Guide — 按认知路径展开正文

典型正文顺序（可以灵活调整，**不是强制小节数**）：

**具体情境 → 错误直觉或既有方案的不足 → 直觉模型/小例子 → 机制/输入输出/边界 → 设计取舍 → 按顺序实践 → 观察与解读 → 故意制造失败 → 常见问题与诊断 → 独立练习 → 验收 → 下一篇真正缺口。**

在每段技术实现处至少回答：为什么要这样设计？这段代码的输入、输出、副作用是什么？不这样做会导致什么？它能证明什么、不能证明什么？

对复杂模块使用两层解释：先用四到八行伪代码/事件流程给读者全景，再解读真正的代码。不要逐行读 Python 语法而忽略系统行为。

### 4. Check — 让读者有可操作的验证

每篇**至少两个不同类型的检验**（适当时）：

- 正例：执行成功后出现什么、属于哪一级证据。
- 反例：改动源码、错误配置、失败测试、无事件等，应该如何诊断。
- 思考：先预测结果，再解释原因或提供提示与答案。

用户要求直接拿到成品时，练习不应阻断交付，也不应要求先回答才能看到后半篇。

### 5. Summarize — 完工边界与衔接

结尾分别说清：已做成的功能、已检验的范围、未检验的内容、下一篇为什么需要做。避免含糊的“系统已经非常智能”“基本生产级”。

### 6. 生产和质量门槛

1. 保持 Markdown 为正文真源；若交付合订本，应从单篇生成，避免两边分叉。
2. 若同时交代码：一个可安装/可执行的源码真源，每篇说明变动，不手工复制出九套不同版本。
3. 对正文运行 `python scripts/lint_blog.py <文章或目录>`，静态问题按严重度处理；脚本无法证明技术结论或教学质量。
4. 对 Python 示例执行语法检查与相关测试；未运行时明确标为示例，绝不编造通过记录。
5. 按 `references/quality-gates.md` 自检；**任何硬阻断问题都应先修复，而不是用总分抵消**。
6. 交付时说明本次真正写了多少篇、有哪些真实文件、测试实际运行了什么、哪些步骤必须在用户电脑再验收。

## 资源按需读取

- `references/style-dna.md`：从用户第 01–04 篇提炼的原文风格、结构特征、不能照搬的历史排版瑕疵。**重写/续写时先读。**
- `references/series-continuity.md`：连载、仓库接口、章节矩阵、逐篇升级时读。
- `references/technical-proof.md`：技术真伪、来源、实验验证、反例、真实发布时读。
- `references/quality-gates.md`：全文交付前的质量门槛和人工评分。
- `references/rewrite-examples.md`：低质量段落如何改成有推导、有实验的高质量讲解。
- `references/feedback-protocol.md`：收到新反馈后，怎样沉淀成可检验的规则与版本。
- `references/tutor-integration.md`：与已有 tutor-skill 的职责分工。
- `assets/chapter-template.md`：单篇 Markdown 可改写骨架；不要留下占位符。
- `assets/series-matrix.md`：连载状态和章节依赖表。
- `assets/usage-prompts.md`：用户在 Codex / 支持 Skill 的 Agent 中调用示例。
- `scripts/scaffold.py`：为指定篇数生成空白博客文件与系列进度矩阵。
- `scripts/lint_blog.py`：检查文章结构、链接和常见残留；不对用户源文件做更改。

## 最后 30 秒校验

- 文章里哪一段最能解释**为什么这么设计**？若找不到，说明只写了操作手册。
- 用户照做后**具体怎样知道成功**？若找不到，说明不具备教学闭环。
- 当前仓库中的入口、函数、CLI、路径是否对得上？若对不上，不得声称“兼容旧项目”。
- 示例输出与真实运行记录有无混淆？是否引用了不存在的文件/图片/链接？
- 删掉长代码后，剩下的解释是否仍然有知识密度？
- 结尾能否诚实地说出还没做到的部分？
