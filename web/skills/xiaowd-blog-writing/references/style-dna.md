# 用户技术博客的写作 DNA（源于原始第 01–04 篇）

> 仅根据用户提供的《从零开发 Agent Watchdog（01）—（04）》提炼。这里写的是**已有原文确实呈现的结构、素材和用户随后指出的改进方向**，并不声称已验证所有 Windows 实机步骤。

## 原文中的稳定写法

| 特征 | 原文中的体现 | 迁移到新主题时怎样做 |
|---|---|---|
| 标题强调项目与增量 | “从零开发 Agent Watchdog（03）：让 AI 的任务进度有证据，而不是只听它说‘完成了’” | “系列名（编号）：读者真实关心的结果/矛盾”，不要只有库名 |
| 先回顾，再揭露缺口 | 第 04 篇从“Logger/Monitor/Evidence 已存在但未联动”起步 | 说明上一篇真正交付了什么，然后找一个切实无法完成的动作 |
| 目标按能力而非概念命名 | 第 01 篇：让事件写入 `events.jsonl`；第 02 篇：动态面板；第 03 篇：独立证据 | 每篇确定一个读者能亲眼看到的能力变化 |
| 解释设计选择 | 第 04 篇强调 Hook 快速返回、Git 扫描放 Bridge 而非 Hook | 给负面场景和替代方案，不能只解释 API 用法 |
| 同一环境连续实践 | Windows 11、Conda `torch_env`、`D:\program\agent_watchdog`、`hook_demo` | 固定实验环境与命令语法；换项目时重新核对，不能复制旧路径 |
| 先隔离，再端到端 | 第 02 篇先模拟 Hook 再连真实 Codex；第 03 篇使用演示仓库 | 每篇给独立小实验，再给真实集成步骤 |
| 反例比口号重要 | 第 03 篇故意修改测试后源码触发 `STALE`、改 `GOAL.md` 触发保护告警 | 用失败/过期/越界等反例教用户理解系统边界 |
| 解释能力边界 | 无事件 ≠ 卡住；Git 有改动 ≠ 一定由 Codex 修改；测试通过 ≠ 任务完成 | 单列“能证明/不能证明”，避免夸大 |
| 前后章衔接明确 | 结尾总结目前已有模块，预告下篇新增监督能力 | 下篇起因必须来自这一篇留下的**实际缺口** |

## 必须保留的文字体验

1. 中文为主、术语第一次出现提供中文说明与英文原词，如 `Baseline（基线）`、`Bridge（事件桥接器）`。
2. 尽量让读者通过小场景看懂术语，而不是开头堆术语清单。
3. 结构化但不干瘪：操作、原理和可观察的输出交替出现。
4. 小节使用自然问题，例如“为什么不让 Hook 直接扫描 Git？”优于“Bridge 原理介绍”。
5. 示例状态要显眼标注“目标效果示意”或“模拟输出”，真实本机验收与其分开。
6. 重要工程判断用贴近工作流的语言解释，不靠炫技和高级形容词。

## 原文也暴露出需要修复的形式问题

这些**不是要模仿的个人风格**：

- 旧 Markdown 留有 `[image](...)` 的站点 favicon 链接、`ChatGPT Learn` 文字、孤立的“下载 Python 文件”占位符等聊天界面导出残留。
- 有的 Python 内容在渲染/粘贴中丢失换行（例如 `import sysimport json...`），可能使读者复制后无法运行。要把完整源代码放入独立 `.py` 文件并运行检查。
- “本地测试通过”但没有可以追溯的命令和完整验证边界时，应补齐证据而不是直接继承断言。
- 长篇教程容易把“演示成果”和“真实工具接入”混淆；两者分开验收。
- 历史版本的文件名、路径或下载入口可能已经失效，不能原样照搬没有核实的旧链接。

## 允许变化的部分

- 若主题是数学证明，替换“路径/命令/CLI”为“定义/前提/推导/反例/习题”；保留教学闭环。
- 若主题是工具经验复盘，替换“完整源码”为“截图/命令/记录/方案比较”；保留验证依据。
- 如果用户只要一篇文章，不要机械加入 20 章规划或 GitHub Release。
- 不把“超级大长文”硬编码成字数线；深度来自例子、推导、边界与检验。
