# 连续工程博客：避免“每篇另起炉灶”

## 研究原项目后先冻结的事实

建立内部或文档化的 `series-matrix`，至少包括：章节、原始用户需求、新增目标、继承文件、新增/修改文件、测试命令、预期状态、实测状态、未解决问题。

按以下顺序校验：

1. 读取仓库 README、最近两篇正文、入口脚本与配置文件。
2. 列出已存在的可调用接口（入口 `main`、函数签名、CLI 参数、状态 JSON 字段）。
3. 区分用户截图中的本机文件、上传压缩包的文件、GitHub 远端文件。三者不必然一致。
4. 找到新增功能的最小改动；先兼容已有 API，不必要不换框架。
5. 如果旧教程有实际错误，用“修正说明/迁移步骤”显式交代，不偷偷改写历史。

## 每章的能力增量

**已知能力 → 不足 → 设计决策 → 文件差异 → 可运行实验 → 验收 → 下章缺口**。

读者应能回答：“如果我只完成这一篇，上一章能力是否还在？新功能是否可独立验证？”

## 代码真源（Source of Truth）

- 同一功能的核心代码只能有一个权威位置；其他文章引用它。按需附章节 checkpoint 或带版本的 tag，但不要出现正文 A 和压缩包 B 两套互斥版本。
- 文章中的路径、入口、文件名应和源码包一致；任何重命名都提供迁移映射表。
- 新依赖只在确有必要时引入，并写清必要性。环境已有 Conda/PyTorch 时不随意重装。
- 文中完整代码很长时：选关键 20–80 行教学 + 提供完整独立源码及精确链接。不要用没有实际生成的“点击下载”。

## 发布仓库策略

- 更新已有文章时，尽量保留第 01–03 篇原文，除非用户明确要求改写。
- 用户要求 GitHub 推送时，先确认当前仓库、分支、覆盖范围；保留非目标文件，运行测试，再提交，核对远端路径。
- 不将原始对话、私钥、Token、浏览器 Cookie、训练日志或开发数据库提交。
- 报告上传成功时必须有工具返回的提交结果或实际远端验证。

## 对系列完工的要求

系列章节数量是规划，不是功能证据。章节“写完”与“读者电脑已跑通”应分别标识：`DRAFT`、`SOURCE_READY`、`LOCAL_TESTED`、`USER_E2E_VERIFIED`。如无证据，不标最后一种。
