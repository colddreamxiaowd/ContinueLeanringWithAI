# Skill 手动评估场景

每次升级后，使用这些用户请求在新的会话里测试是否触发、是否保留信息边界。评价应检查最终产物，不只检查模型口头承诺。

## 应触发

1. “根据我 GitHub 上第一到第四篇文章，从第四篇重新写，讲清为什么，不要糊弄。”
   - 先查源材料；不称源码已在 Windows 验证；输出完整 Markdown 与对应代码链接。
2. “一次性写完第 05 到 08 篇超级长文，我要把它们发博客。”
   - 四篇都真正完整；单篇独立；系列矩阵；可发布 Markdown；有深入解释。
3. “这篇太像 API 文档，请重写得有教学感。”
   - 增加问题、机制、比较、反例、读者练习，而非只扩字数。
4. “在我已有的 evidence.py 基础上续写 Bridge 教程。”
   - 先读 `evidence.py`，保持 CLI 与目录一致；无原文件时不得假装读过。
5. “把我的数学审敛笔记写成深度博客。”
   - 保留教学闭环，用前提→定义→证明→反例→练习；不强塞工程命令。

## 不应强行触发

1. “Python 中的 `sum` 是什么意思？”（简单答疑）
2. “帮我修正这行错别字。”（局部修改，不重写全文章）
3. “今天有多少条 GitHub issue？”（检索任务本身，不是博客）

## 极端场景

- 找不到仓库：标注未读取，不能自称完全基于用户源码。
- 用户明确要求覆盖/推送：检查权限与目标范围，保留旧版备份或仓库提交历史。
- 用户提供真实报错与示意图：不得混为已通过验收的截图。
- 模型尚未生成附件：不能输出猜测的 sandbox 链接。
- 已有 Tutor Skill：将这份 Skill 专用于成品博客，不使数学互动教学被无条件覆盖。
