# 技术解释、来源与验收证据

## 关键概念须讲透

写到新概念时用六个问题诊断是否讲透：

1. 现实里出现了什么失败或需求？
2. 为什么之前的方法不够？
3. 新组件吃什么输入、产生什么输出、有什么副作用？
4. 核心步骤为什么按这个顺序？替代设计有什么代价？
5. 读者如何亲手观察正确情形与错误情形？
6. 哪些结论不能由这次实验推出？

例如讲 JSONL vs SQLite 时，不只写“SQLite 更专业”：必须展示重启、重复导入、事件编号冲突等具体情景；再解释游标、唯一约束、事务等机制的边界。

## 证据分层用词

| 等级 | 可用表达 | 不可夸大的表述 |
|---|---|---|
| 用户给出本机终端输出 | “根据你提供的 Windows 输出，当前命令在那次运行中……” | “我们已验证所有系统路径与长期稳定性” |
| 本轮工具隔离测试 | “在当前隔离环境对所附示例执行 X 测试通过” | “你的电脑上已经运行成功” |
| 仅代码审阅 | “静态检查显示存在/没有看到某种情况” | “功能已端到端通过” |
| 未运行例子 | “正常时预期出现如下结果（示意）” | “实测显示以下输出” |
| 模型推断/启发式 | “可能存在风险，建议检查” | “已经证明卡死/越权” |

## 引用

- API、版本、规格、命令语法：优先官方手册、仓库源码、发行说明。
- 源信息只说明作者/工具曾说了什么，不自动等于真实结论。
- 失效链接不可留给读者当成可下载源码；所有相对链接需要检查文件是否存在。
- 不把 URL 拼接错误、HTML 转义残留、ChatGPT 组件地址或站点 favicon 当有效参考文献。

## 操作安全

- 指定 `cmd` / `powershell` / `bash`；不要把 CMD 的 `cd /d` 写入 PowerShell 代码围栏。
- 运行不可信脚本、连接外部账号、删改用户文件、修改 Git 全局设置、推送远端都需要适当授权与防护。
- 对 Agent 轨迹做最小化采集，避免保存原始系统提示、密码、环境变量和工具输出。
- 验证状态机时同时测成功、失败、过期、无法判定、权限不足。
